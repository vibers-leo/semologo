## 5차 — 검색 크래시 (2026-08-17)

**사이트가 죽고 있었다.** 초성을 한 글자만 쳐도 `This page couldn't load`.

원인은 4차에서 넣은 해외 프리셋(film·investor)이다. 그 프리셋들은 한글명을
필수로 걸지 않는데, **없는 값을 그대로 `null` 로 brands.json 에 썼다(126건).**
`choseongIndex(raw, b.name_ko)` 가 null 에 `.replace` 를 호출해 던졌고,
렌더 중 예외라 화면 전체가 멈췄다.

네 겹으로 막았다:
| 지점 | 조치 |
|---|---|
| 데이터 | null name_ko 126건을 영문명으로 채움 (+ 빈 name_en 15건 복원) |
| 코드 | `choseongIndex` 가 null/undefined 를 받아도 -1 |
| 수집기 | `ko or en or slug` 폴백 — null 을 쓰지 않는다 |
| 검사 | `check-assets` 가 빈 name_ko/name_en 을 **실패**로 잡는다 |

**교훈: 데이터 한 줄이 잘못됐다고 화면 전체가 죽으면 안 된다.**
검색·렌더 경로의 문자열 함수는 null 을 받아도 살아남아야 한다.

검증: headless 로 `ㄱ`·`ㅇㅌ`·`가`·`a`·`ㅅㅅ` 입력 — PAGEERROR·크래시 0건.

그냥 트레이싱하면 계단이 심해서, 24배 확대 후 가우시안 블러 → 임계값으로

SVG 대기 목록에도 남겼다.

## 6차 — 부족한 곳 진단 후 추천 순서대로 (2026-08-17)

사용자가 "어떤 부분이 부족해 보이냐"고 물어 **측정으로 답했다.**

### 진단
| 문제 | 실측 |
|---|---|
| 편중 | IT·테크 4,616(63%) vs 식품 69·유통 63·교육 19 |
| 한글로 못 찾음 | 5,327 (72%) — IT·테크는 14%만 검색 가능 |
| 일상 브랜드 구멍 | 표본 90개 중 21개 없음. **공공·생활이 최악(3/8)** |

원인 분해가 결정적이었다 — **못 찾는 5,327개 중 3,632개(68%)가 도메인이 없어
기존 도구가 조회조차 못 하고 있었다.**

### 1번 — 한글 별칭 (28% → 35%)
도메인이 없으면 P856 대조를 못 하니 다른 3중 가드를 세웠다:
이름 정확일치 + 분류가 조직·제품 계열 + **공식 웹사이트 보유**.
세 번째가 결정타다 — 개념어엔 웹사이트가 없어서 `Vector→벡터`,
`Cube→큐브` 류 일반명사 오답이 걸러진다. 575건 반영.

**반영하지 않은 것이 가드의 값어치를 증명한다.** '이름은 맞는데 도메인이 다른'
373건은 대부분 오답이었다: `v0→포구속도` · `Framework→액자` · `O2→이산소` ·
`BT→생명공학기술` · `Ram→랜덤 액세스 메모리`.

### 2번 — 공식 사이트 SVG 수집기 (신규)
한국 일상 브랜드는 위키데이터에 로고를 안 올린다. **렌더링한 뒤** DOM 에서
SVG 를 뽑는다 — 정적 HTML 로는 안 나온다(전부 SPA).

18곳 중 10곳에서 SVG 를 얻었고, 대조 시트로 **4건을 걸렀다**:
· 노브랜드 → **삼성카드 배너**를 잡았다(이마트 페이지 광고)
· 국민건강보험 → 정부 상징만 / 국민연금 → 장식 곡선 / 맘스터치 → 일부만
9건 등록: 번개장터·쿠팡이츠·닥터나우·굿닥·패스트캠퍼스·중고나라·
왓챠피디아·윌라·국세청.

### 그 과정에서 찾은 더 큰 문제 — 내가 만든 중복 13쌍
`naver ↔ naver-corporation`, `kr-moj ↔ ministry-of-justice` …
**수집 당시 기존 항목의 name_ko 가 영문("Naver")이라** 새 한글명("네이버")과
매칭되지 않았다. 한글명을 나중에 채운 시점 차이가 그대로 구멍이 됐다.

기존 id 를 대표로 살리고(색인·링크 보호) 신규 로고는 변형으로 흡수했다.
수집기는 이름을 정규화하고 **별칭까지 대조**하도록 고쳤다 —
재실행에서 '이미 보유'가 434 → 529 로 늘어 막히는 것을 확인했다.

국세청도 3개(kr-nts·hometax·national-tax-service-of-south-korea)로 갈라져
있어 하나로 합치고 가로·세로 변형으로 정리했다.

### 결과
브랜드 7,357 → **7,351**(중복 정리 후) · 한글 검색 **28% → 35%**

## 8차 — 로딩·무한스크롤 + 정렬 뒤집힘 (2026-08-17)

### 무한스크롤은 "안 되는" 게 아니라 "느린" 것이었다
실측하니 30 → 60 → 90 으로 **동작은 하고 있었다.** 한 번에 30개, 500ms 쿨다운,
바닥 200px 앞에서야 발화 — 6,879개짜리 목록에선 벽에 부딪히는 느낌이 난다.
60개 / 250ms / rootMargin 1200px 로 바꿨다. 이미지는 `loading="lazy"` 라
DOM 카드가 늘어도 즉시 요청되지 않는다.

### 로딩 — HTML 은 193ms 인데 카드는 1,000ms 에 떴다
빈 화면 800ms 가 통째로 **클라이언트가 brands-slim.json 을 받아 파싱하는 시간**
이었다. 빌드 시점에 첫 60장을 서버에서 렌더해 넘기도록 바꿨다.
지금은 **DOMContentLoaded(153ms) 시점에 이미 카드 60개가 있다.**

### 그 과정에서 만든 버그 — 정렬이 뒤집혔다
서버가 정렬한 60장을 클라이언트가 **한 번 더 정렬**하면서 순서가 통째로
뒤집혔다. `sortForGrid` 가 보조 기준으로 **넘겨받은 배열의 위치**를 썼기
때문이다 — kspo 는 0번이라 오히려 맨 뒤로 가고 오래된 브랜드가 앞에 왔다.

원인을 찾는 데 오래 걸렸다. CF 캐시·GitHub Pages 캐시·빌드 캐시를 차례로
의심했고 전부 아니었다. **빌드 로그에 실제 받은 데이터를 찍어서** 데이터는
정확하다는 것을 확인한 뒤에야 정렬 함수 쪽으로 눈을 돌릴 수 있었다.

고침: `brands-slim.json` 이 `seq`(brands.json 에서의 위치 = 추가 순서)를 싣고,
정렬은 그걸 쓴다. **몇 번을 정렬해도 결과가 같다** — 멱등성을 실측으로 확인했다.

코나아이·한국가스안전공사·대한체육회·라자드·SK뷰·SSG페이·세계태권도연맹·한패스.
