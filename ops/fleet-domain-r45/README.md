# SemoLogo Windows domain-discovery release r45

`runtime/` contains only the files added or changed relative to the already deployed shared fleet r44a release. Do not build a Windows handoff from the older local `ops/worker-fleet/deployment/package-windows.py` allowlist; it omits unrelated production modules. Start from the verified credential-free r44a handoff SHA in `release-manifest.json`, replace these files, update `bundle-manifest.json` hashes, and publish the new immutable package.

The server image layers `core.mjs`, `server.mjs`, `artifacts.mjs`, `semologo-domain-discover.mjs`, and `version.mjs` over `vibers-fleet:20261017-subscription-scale-r44a`. Windows also receives `worker.mjs`. The `semologo-domain-discover` job accepts 1–12 distinct domains in one queue item, checks public HTTPS and robots rules, and writes URL signals to a private result manifest marked `PENDING`. It does not download/publish logos. The Mac must fetch and review the SVG before CMS publication.

Deployment sequence used: server image and `check-deploy.sh` → credential-free Windows handoff to bucket and auto-update feed → config job allowlist → one pilot job per PC → bucket manifest verification and r45 diagnostics → recurring feeder. The feeder source is [queue-worker-domain-shards-20261017.cjs](../../scripts/queue-worker-domain-shards-20261017.cjs), and its timer units are in [ops/systemd](../systemd). The bucket and job IDs are recorded in [semologo-domain-fleet-20261017.json](../../data/collection/semologo-domain-fleet-20261017.json).

The live server was re-based on r44a after a concurrent shared-fleet release changed the image during preparation. All unrelated server modules were inherited from r44a; activation first aborted when the expected base image changed. The pre-r45 container remains named `vibers-fleet-before-domain-r45` for rollback. The r45 worker handoff SHA is pinned in the release manifest; both Windows diagnostics returned `20261017-semologo-domain-r45`.

## File staging and publication

The timer automatically discovers URL signals; it does **not** publish them. On the central Mac, `python3 scripts/stage-fleet-domain-assets.py --limit-jobs 500 --workers 24 --output /Volumes/HDD-1TB/semologo-migration/bulk-staging/<batch>` verifies immutable fleet manifests and downloads bounded first-party SVG/PNG/WebP files to a private, content-addressed directory. The output `manifest.json` retains source domain, page, asset URL, hash, format and failure reason. Run it again with a new batch directory to process later jobs. No CMS write occurs in this stage.

The 2026-10-17 pass read 412 successful Windows jobs, staged 2,303 unique files from 1,282 domains, and published 26 visually reviewed new brands using `scripts/publish-commons-taiwan-new-20261017.py` with the reviewed manifest in `data/collection/windows-domain-bulk-20261017.json`. See `data/collection/windows-domain-bulk-staging-20261017.json` for counts. The remaining files need identity, visual, SVG-safety and duplication review before any public CMS update. The staging pass currently runs on demand; a recurring central-Mac scheduler has not been installed.

Rollback order, if the new job affects shared fleet work: stop `semologo-domain-discover.timer`, wait for active leases to finish, restore the server config from `/root/projects/vibers-fleet/secrets/config-before-semologo-domain-r45.json`, replace the r45 container with `vibers-fleet-before-domain-r45`, and run `/root/check-deploy.sh vibers-fleet http://127.0.0.1:4781/fleet/healthz`. Republish the verified r44a Windows handoff hash from `release-manifest.json` before re-enabling worker schedules. The bucket seed shards and CMS publications do not need to be deleted for a fleet rollback.
